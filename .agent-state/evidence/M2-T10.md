## Design followed

Implemented to `.agent-state/design/M2-T10-selectors-xpath-design.md`
(§0–§8) with two disclosed, deliberate deviations from the letter of the
design doc, both documented at the point they occur in source comments too:

1. **Matcher representation (§2, §8)**: the design describes a compiled
   selector as "a reversed sequence — rightmost compound first." This crate
   parses `ComplexSelector.compounds`/`.combinators` in natural left-to-right
   source order and has the matcher walk right-to-left via a *decrementing
   index* (`match_at(..., idx)` starts at `compounds.len() - 1` and recurses
   toward `0`). This is algorithmically identical to the design's reversed-
   sequence representation (same rightmost-first testing order, same
   backtracking shape per combinator) without a separate reversal pass at
   parse time — documented in `css/ast.rs`'s `ComplexSelector` doc comment.
2. **Tokenizer/parser split for `:nth-child`'s `an+b` micro-syntax (§8)**:
   rather than teaching the general CSS tokenizer the `an+b` dimension
   grammar (a well-known special case even in the CSS spec's own
   tokenizer), `css/parser.rs::parse_nth_argument` extracts the raw token
   range between `nth-child(`/`nth-last-child(` and its matching `)` and
   hands it to a small dedicated parser (`css/pseudo.rs::parse_nth`). Both
   are still staged strictly before matching begins (two-phase preserved);
   only the internal token-vs-string boundary for this one construct moved.

Everything else — grammar scope (§1), match-order/backtracking algorithm
(§2), no-indexing MVP (§3), `Revision`-stamped results (§4),
XPath axis/predicate scope and the `XPathItem::Attribute` gap-closing
design (§5), the three-way `QueryError` split (§6), and the module layout
(§8, `css/`+`xpath/` as sibling modules of one crate) — was implemented as
specified.

## What shipped

### CSS selectors (`css/`)

- **Grammar** (`css/ast.rs`, `css/tokenizer.rs`, `css/parser.rs`): universal
  (`*`), type, class, id, attribute selectors with all 6 operators (`[attr]`,
  `=`, `~=`, `|=`, `^=`, `$=`, `*=`), descendant/child/adjacent-sibling/
  general-sibling combinators, selector lists (`,`), and
  `:first-child`/`:last-child`/`:only-child`/`:nth-child(an+b)`/
  `:nth-last-child(an+b)`/`:empty`/`:root`/`:not(<compound>)` — exactly the
  design §1 priority list. Tag names are lowercased at parse time (matches
  M2-T04's tree-builder folding, documented rather than re-implemented);
  attribute values match case-sensitively.
- **Matcher** (`css/matcher.rs`): right-to-left, bounded-backtracking, per
  design §2. Compound-match order is cheapest-first via
  `SimpleSelector::match_cost_rank` (id/type/universal → class/attribute-
  presence → attribute-value operators/`:not()` → structural pseudo-classes
  last), applied by sorting each compound's simple-selector list once at
  parse time. Descendant/general-sibling walks backtrack across every
  candidate ancestor/sibling (tested explicitly — see "Test coverage"
  below), bounded by `machina_dom::MAX_ANCESTOR_WALK` (reused directly, not
  mirrored).
- **Query entry points** (`query.rs`): `query_selector_all`,
  `query_selector`, `matches` (single already-resolved element), and direct
  `get_element_by_id`/`get_elements_by_class_name`/`get_elements_by_tag_name`
  fast paths that bypass the CSS parser entirely (raw string/attribute
  comparison, per design §3 — also avoids misinterpreting a literal id/class
  value containing CSS metacharacters). One shared iterative (explicit-
  stack, never recursive) pre-order document-order DFS
  (`walk_document_order`) backs all of them; no incrementally-maintained
  index, per the design's deliberate no-indexing MVP decision (§3).
- **Compile-once API** (`css/mod.rs`): `parse_selector`/`matches_compiled`
  expose the `Document`-agnostic `SelectorList` AST directly for a caller
  that wants to compile once and match many elements without re-parsing
  (design §4a).

### XPath (`xpath/`)

- **Grammar** (`xpath/ast.rs`, `xpath/tokenizer.rs`, `xpath/parser.rs`):
  absolute/relative location paths, `//` abbreviation, the five in-scope
  axes (`child::`/default, `descendant::`/`//`, `attribute::`/`@`,
  `self::`/`.`, `parent::`/`..`), node tests (element name, `*`, `text()`,
  `node()`, `comment()`), and predicates (`[N]`, `[last()]`, `[@attr]`,
  `[@attr='v']`, `and`-chains) — design §5 exactly.
- **Evaluator** (`xpath/evaluator.rs`): per-context axis expansion, then
  per-predicate filtering against that context's own candidate list
  (positions re-anchor correctly across chained predicates), then a
  document-order-preserving, first-occurrence dedupe across contexts
  (`dedupe_preserving_order`) — tested directly (`results_are_deduplicated_
  and_in_document_order_across_multiple_contexts`).
- **`XPathItem::{Node, Attribute}`** (design §5's attribute-axis result
  gap): `Attribute { owner: ElementHandle, name: String, value: String }`
  closes the real gap that `machina_dom`'s `AttributeMap` has no arena
  `NodeHandle` for an attribute. `evaluate_xpath(document, expr, context:
  Option<NodeHandle>)`: absolute paths ignore `context`; a relative path
  with `context: None` fails with `QueryError::ContextNodeRequired`, never
  silently defaults to the document root (tested:
  `relative_xpath_without_context_node_is_a_dedicated_error_not_a_silent_default`).
- `//` combined with an explicit axis specifier on the same step (e.g.
  `//@id`, `//self::x`) is rejected as `UnsupportedFeature` rather than
  guessed at — a narrower interpretation than full XPath's
  `descendant-or-self::node()` expansion, disclosed in `xpath/parser.rs`'s
  `parse_step` doc comments; the common real-world shape (`//button/@id`,
  where `//` applies to `button` and `@id` is a separate, later, ordinary
  step) works correctly and is tested (`attribute_axis_produces_a_distinct_
  attribute_item`).

### Shared error handling (`error.rs`)

`QueryError` — `InvalidSelector`/`InvalidXPath` (malformed syntax, staged
strictly before matching/evaluation begins), `UnsupportedFeature` (valid
CSS/XPath this crate does not implement — a curated
`KNOWN_UNSUPPORTED_PSEUDO_CLASSES`/`KNOWN_UNSUPPORTED_AXES` list drives this
branch), `TooComplex { limit: LimitKind }`, `ContextNodeRequired`,
`DomError(DomError)` (via `From`). `#[non_exhaustive]` on both `QueryError`
and `LimitKind` so a future added variant is not a breaking change for
callers matching exhaustively today.

## Deviations / honest gaps disclosed (not silently cut)

1. **Unknown (not curated-list, not grammar-recognized) pseudo-class names
   are classified as `InvalidSelector`, not `UnsupportedFeature`.** There is
   no practical way to distinguish "obscure-but-real future/draft CSS
   pseudo-class this crate hasn't heard of" from "a typo" without an
   exhaustive, externally-maintained spec-derived list; the curated
   `KNOWN_UNSUPPORTED_PSEUDO_CLASSES`/`KNOWN_UNSUPPORTED_AXES` constants in
   `css/parser.rs`/`xpath/parser.rs` cover every pseudo-class/axis named in
   the design doc's own "explicitly deferred" list (§1/§5) plus the common
   remaining Selectors-4/HTML pseudo-classes, so this only affects genuinely
   unrecognized input, not anything the design doc named.
2. **XPath's `and`-only predicate combination has no `or`/`not()`/
   parenthesized boolean sub-expressions** (design §5 explicitly scopes
   this out) — any of those produce `UnsupportedFeature` at the point the
   unrecognized token/function is reached, never a partial/wrong
   evaluation.
3. **The XPath tokenizer accepts `,` even though no in-scope construct uses
   it**, specifically so a multi-argument unsupported function call like
   `contains(text(), 'x')` fails via the parser's `UnsupportedFeature`
   classification instead of an unrelated tokenizer-level `InvalidXPath` on
   the comma character (comma is genuine, valid XPath syntax — just for
   functions this crate does not implement). Documented in
   `xpath/tokenizer.rs`'s `Token::Comma` doc comment; found and fixed during
   this task's own error-classification test-writing (see "Process notes"
   below).
4. **The CSS tokenizer's `is_ident_start` is deliberately broader than the
   CSS spec's own `ident-start-code-point`** (it also accepts ASCII digits)
   so `:nth-child(2n+1)`/`:nth-child(3)`-style digit-leading content
   tokenizes as ident-like blobs for `css/pseudo.rs::parse_nth` to
   reconstruct, without a separate numeric-dimension token type. Documented
   in `css/tokenizer.rs`; harmless elsewhere since HTML tag/attribute names
   never start with a digit, so a digit-leading token used as a type/class/
   id selector simply never matches real content — not a silent-mismatch
   hazard.

  `crates/selectors/tests/**` (test-only fixture-building code over fixed
  input), matching the same precedent.
- **No fabricated WPT conformance**: none claimed; explicitly named as
  deferred, real, tracked infrastructure work throughout this document.
- **No other crate's source touched**: `git diff origin/main...HEAD --stat`
  (reproduced above under "Changed files") shows only `crates/selectors/**`,
  the two-line `Cargo.toml`/`Cargo.lock` root-manifest change, and this

- **No silent no-op for an unsupported construct**: every valid-but-out-of-
