## Real API verification before building against it (required by task instructions)

Read directly, in full, before writing any `crates/semantic` source:
`crates/dom/src/{lib,document,node,handle,attributes,error}.rs`,
`crates/selectors/src/{lib,query,error,limits}.rs`,
`crates/selectors/src/css/{mod,ast}.rs`, `crates/html-tree-builder/src/
{lib,builder}.rs` (public API surface only), and
`.agent-state/design/M2-T10-selectors-xpath-design.md` §4 ("Cache
invalidation via `Revision`") and `.agent-state/design/
M2-M1-contract-compatibility-checklist.md`.

Key findings that shaped the implementation:

- **No `attribute_names()`/enumeration method exists on `Document`** —
  confirmed via M2-T10's own evidence doc and by reading `document.rs`
  directly. This crate never needed one: every attribute this crate reads
  is looked up by a specific, known name (`role`, `aria-label`, `alt`,
  `href`, `id`, `for`, `type`, `multiple`, `placeholder`, `action`,
  `method`, `charset`, `content`, `name`, `property`, `http-equiv`, `lang`),
  never enumerated.
- **`AttributeMap`/`Document::attribute` has no case-insensitive lookup and
  no way to compare an attribute value against an arbitrary caller-supplied
  string safely except via direct Rust string comparison** — this is why
  `role.rs::label_derived_name`/`extract.rs::build_label_map` resolve
  `<label for="...">` by building a `HashMap<String, ElementHandle>` from a
  single document-wide walk and comparing raw attribute-value strings
  directly, rather than interpolating a control's `id` attribute value into
  a CSS selector string (`format!("label[for=\"{id}\"]")`) and querying
  per-control. The latter would have been both less efficient (one query
  per control instead of one walk total) and a real injection-shaped
  hazard: `id` is live, adversarial page content and could contain `"` or
  other CSS metacharacters. Documented in `extract.rs::build_label_map`'s
  doc comment.
- **`Document::children(parent)` returns tree-order children for *any* node
  handle, including `Text`/`Comment`/`DocumentType`, returning an empty
  `Vec` rather than an error for kinds with no children** — verified via
  `crates/dom/src/mutation.rs::collect_children`, which walks
  `first_child`/`next_sibling` links unconditionally rather than switching
  on node kind. This let `markdown.rs`'s traversal treat `Document`/
  `DocumentFragment` as transparent containers uniformly rather than
  needing a special case.
- **`Revision` is `Copy`/`Eq`/`Ord` with only a `value()` accessor** — this
  crate's three result types (`SemanticIndex`, `MarkdownDocument`,
  `DocumentMetadata`) each store it directly and compare via `!=`/`>`
  against a fresh `document.revision()` call, exactly matching M2-T10's
  established contract (verified by direct test — see "Test coverage"
  below).
- **`machina_selectors::css::{parse_selector, matches_compiled}` (design
  §4a's "compile-once" API) is the exact integration point this task's
  briefing named** ("use it for locating interactive elements/headings/
  links/forms rather than writing your own tree-walk-and-match logic from
  scratch"): `extract.rs` compiles one fixed candidate selector once per
  `extract_semantic_index` call and tests each element against it via
  `matches_compiled` during this crate's own single document-order DFS,
  rather than either (a) writing a second independent tag/attribute-match
  function, or (b) calling `machina_selectors::query_selector_all`
  separately per category (which would re-walk the whole tree once per
  category — headings, links, forms, interactive — instead of once total).
- **`machina_selectors::query::walk_document_order` (the shared
  document-order DFS) is `pub(crate)` to `crates/selectors`, not exported**
  — confirmed via `crates/selectors/src/lib.rs`'s `pub use` list. This crate
  therefore has its own copy of the same bounded-walk shape
  (`crates/semantic/src/walk.rs`) rather than taking a dependency on a
  private helper; documented in that file's module doc comment as a
  deliberate, disclosed duplication of *shape*, not of DOM data.
- Confirmed no `unsafe` and no `unwrap`/`expect` on any DOM-content-reachable
  path anywhere in `crates/dom/src/**` and `crates/selectors/src/**`
  (matching both crates' own evidence-doc claims) — this crate's own bar is
  therefore layered on top of already-panic-free dependencies.

### 1. Crate placement and dependency shape

including `semantic`, and its "keep `[dependencies]` limited to

any of those (it is a pure engine-layer DOM-reading crate, not a
command-bus-facing one), so it depends on neither. Matches the
`dom -> {html-tree-builder, selectors, events} -> semantic` layering
diagram the task briefing described. `machina-html`/`machina-html-tree-
builder` are `dev-dependencies` only (test-fixture construction via real
HTML parsing — see "Test strategy" below), never a production dependency:
this crate operates on an already-built `Document`, it does not parse HTML

### 2. Semantic role/accessible-name derivation subset (deliverable 1)

**Role** (`src/role.rs`): an explicit `role="..."` attribute always wins
(first whitespace-separated token, lowercased — no fallback-list walking of
subsequent tokens if the first is unrecognized). Otherwise, a curated,
hand-written implicit-role table for exactly the elements the task
briefing names (headings, links, interactive elements, forms) plus a
handful of common structural/landmark tags:

| Tag / condition | Role |
|---|---|
| `h1`-`h6` | `heading` (plus a separate `heading_level: Option<u8>` field, 1-6) |
| `a[href]` | `link` (bare `a` with no `href`: no role - matches HTML-AAM) |
| `button`, `summary` | `button` |
| `input[type=button/submit/reset/image]` | `button` |
| `input[type=checkbox]` | `checkbox` |
| `input[type=radio]` | `radio` |
| `input[type=range]` | `slider` |
| `input[type=search]` | `searchbox` |
| `input[type=hidden]` | *(none - never user-interactive)* |
| `input` (any other/unset type) | `textbox` (HTML-AAM's own default) |
| `select[multiple]` | `listbox` |
| `select` (no `multiple`) | `combobox` |
| `textarea` | `textbox` |
| `nav` | `navigation` |
| `main` | `main` |
| `form` | `form` |
| `img` | `img` |
| `ul`/`ol` | `list` |
| `li` | `listitem` |
| `table` | `table` |
| everything else | *(none)* |

**Explicitly not implemented, disclosed** (this is the "basic subset, not a
full ARIA computation engine" the task briefing asked for): the ARIA
role-fallback list (trying a second/third token in `role="foo bar"` if
`foo` is unrecognized); presentational-role conflict resolution; the
`header`/`footer` "is it a landmark or not" ancestor-context rule (HTML-AAM
makes this conditional on whether the element is a descendant of
`article`/`aside`/`main`/`nav`/`section` - this crate does not implement
`header`/`footer` roles at all rather than getting that condition wrong
silently); `dialog`, `details`, `fieldset`/`legend`, `caption`,
`figure`/`figcaption`; any ARIA 1.2 role beyond the table above.

**Accessible name** (`src/role.rs::derive_accessible_name`): `aria-label`
first (normalized/bounded), then `alt` for `img`, then for form controls
(`input`/`textarea`/`select`) an associated `<label for="...">` (resolved
via a document-wide `for`-map built once, see "No duplicate DOM copies"
below) or a wrapping `<label>` ancestor, falling back to `placeholder`,
then a bounded whitespace-collapsed text-content fallback for everything
else - **except `<form>`, which deliberately does not fall through to the
text-content fallback** (a form's aggregate descendant text is not a
meaningful "name" and would be both misleading and expensive to compute
for a large form; only an explicit `aria-label` names a form in this
crate's scope). **Not implemented, disclosed**: `aria-labelledby`
(ID-reference resolution), `aria-describedby`, the `title`-attribute
fallback, `<caption>`/`<legend>`/`<figcaption>` association, and the full
W3C accname-1.2 precedence algorithm (which also accounts for
visibility/`aria-hidden`/`display:none` - this crate has no layout/CSS
model at all, matching M2-T05's own explicit non-goal).

### 3. Interactive-element/heading/link/form indexing (deliverable 2)

**Derived once per `extract_semantic_index` call, never maintained
incrementally** - matches `crates/selectors`'s own design §3 "no-indexing
MVP" decision exactly, for the same reasons (no layout/large-document-heavy
workload in scope for M2; an incrementally-maintained index would need its
own mutation-observer hook and its own teardown/consistency discipline,
duplicating the stale-derived-state bug class M2-T05 already solved once
for the tree itself).

**Two full-document passes, both reading directly from the live
`Document`:**
1. `extract.rs::build_label_map` - one DFS collecting every `<label
   for="...">`'s `for` value -> label element (see "Real API verification"
   above for why this is a map-then-lookup design, not a per-control CSS
   query).
2. The main pass - one DFS testing each element against a single, fixed,
   hand-written candidate selector
   (`"a, button, input, select, textarea, h1, h2, h3, h4, h5, h6, nav,
   main, form, img, ul, ol, li, table, summary, [role]"`), **compiled once
   via `machina_selectors::css::parse_selector` and tested per element via
   `matches_compiled`** - the concrete `machina-selectors` integration
   point. Elements that don't match the candidate selector skip role/name
   computation entirely (cheap short-circuit for the common case of
   `div`/`span`/plain text wrappers, which are the majority of real-page
   elements).

`headings`/`links`/`interactive_elements` are computed as **filters over the
same `roles` vector built by that one pass** (heading = `heading_level.
is_some()`; link = `role == "link"`; interactive = `role` is one of a
curated `INTERACTIVE_ROLES` list) - not four separate tree walks. `forms`
needs its own small second step (`extract.rs::build_forms`): for each
`<form>` element found during the main pass, associate every `input`/
`select`/`textarea`/`button` from `roles` whose nearest `<form>` ancestor
(a small, bounded upward parent-chain walk, `MAX_ANCESTOR_LOOKUP_WALK =
64`) is that form. **Disclosed scope limit**: this is *descendant*-based
association only - HTML's `form="other-form-id"` attribute (associating a
control with a form it is *not* a DOM descendant of) is not resolved.

**Interactive-element scope note, disclosed**: membership is role-driven
(`INTERACTIVE_ROLES = [button, link, checkbox, radio, combobox, listbox,
slider, textbox, searchbox]`). A custom widget that carries `tabindex` but
no ARIA role (a common but non-conformant real-world pattern, e.g. `<div
tabindex="0" onclick="...">`) is **not** flagged interactive by this pass -
a real, disclosed gap, not a silent one.

### 4. Markdown generation (deliverable 2)

**Scope, explicitly**: headings (`h1`-`h6`), paragraphs, unordered/ordered
lists (including nesting, with indentation), links, bold (`strong`/`b`),
italic (`em`/`i`), inline `code`, `<pre>` code fences, images, horizontal
rules, and blockquotes get dedicated Markdown syntax. Every other element
is a transparent pass-through container - block-level ones (`div`,
`section`, `article`, table cells, `form`, ...) get paragraph-style
spacing, inline-level ones (`span`, ...) do not. `<script>`/`<style>`/
`<template>`/`<noscript>`/`<head>` subtrees are excluded entirely (their
content never becomes visible markdown text - verified directly by test,
see below). **This is a "readable markdown" bar, explicitly not a
CommonMark-spec-compliant round-trip** (no table-grid markdown, no
definition lists, no footnotes, no reference-style links, no HTML-entity
edge-case handling beyond what the tokenizer/tree builder already decoded
upstream).

**Implementation**: `markdown.rs::generate_markdown` is one iterative
(`Open`/`Close` explicit-frame-stack, never recursive) traversal of the
live `Document`, the same shape `crates/html-tree-builder`'s test `render()`
helper and `crates/selectors`'s `walk_document_order` use - a
pathologically deep tree cannot blow this crate's call stack. No parallel
tree is built; only the output `String` and a small `Vec<ListKind>`
list-nesting stack are allocated.

**Bounded, not paginated** (the acceptance criterion's literal wording is
"bounded/paginated" - this crate implements the bounded half and discloses
the pagination gap): output is capped at `MAX_MARKDOWN_BYTES = 200_000`
bytes; exceeding it truncates at the nearest `char` boundary, appends a
visible `"...[truncated]"` marker, and sets `MarkdownDocument::truncated =
true`. There is no cursor/offset-based continuation to resume generation
past a truncation point within a single call - a caller that needs the
rest of an oversized document today must call `generate_markdown` on a
narrower subtree via a future scoped-extraction API (not built in this
pass - see "Deferred" below).

### 5. Metadata/schema extraction (deliverable 2)

**In scope**: document `title` (first `<title>` element's bounded,
whitespace-normalized text content), the root `<html lang="...">`
attribute, and every `<meta>` element expressed as one `(key, value)` pair:
`charset` attribute alone, or `content` paired with whichever of
`name`/`property` (Open-Graph-style)/`http-equiv` is present (checked in
that order). Bounded to `MAX_SEMANTIC_ITEMS` total `meta` entries and
`MAX_METADATA_VALUE_CHARS` per value, matching the same
bounded-output posture as everything else in this crate.

**Out of scope, disclosed**: JSON-LD (`<script type="application/
ld+json">`) structured-data parsing, microdata (`itemprop`/`itemscope`),
RDFa, and `<link>` tag extraction (canonical URL, favicon, alternate
stylesheets, ...). None of these are silently mis-extracted - they are
simply not walked by this pass, a real, tracked gap for a later task
(consistent with the task briefing's own "keep this scoped, don't
over-build" instruction for this deliverable).

### 6. Stable handles + revision attachment (deliverable 3)

Every extracted item (`SemanticNode` for roles/headings/interactive
elements, `LinkNode`, `FormNode`) carries the `ElementHandle` it was
derived from. Every top-level result (`SemanticIndex`, `MarkdownDocument`,
`DocumentMetadata`) self-stamps with `document.revision()` at the moment
extraction completed - exactly mirroring `machina_selectors::QueryResult`/
`XPathResult`'s contract: staleness detection is plain `result.revision !=
document.revision()`, never guessed or implicit. No internal cache exists
anywhere in this crate - every public function is a fresh computation
against the `Document` passed in (same "thin layer on top" choice
`crates/selectors` made).

### 7. No duplicate DOM copies (deliverable/acceptance criterion)

Every extraction function reads directly from the live `Document`/
`ElementHandle`s: `grep -rn "clone_node" crates/semantic/src/` finds only
one hit, a doc-comment reference in `text.rs` describing `machina_dom`'s
*own* iterative posture (not a call in this crate). `grep -rn "\.clone()"
crates/semantic/src/` finds only clones of this crate's own small owned
output types (`SemanticNode`, `String`, `Option<String>`) when the same
computed node needs to be pushed into more than one output vector (for
example a heading is pushed into both `roles` and `headings`) - never a
DOM node, subtree, or arena-backed structure. No `Vec<Node>`/parallel-tree
type is defined anywhere in this crate; the only non-trivial allocations
are `Vec<ElementHandle>`, `HashMap<String, ElementHandle>` (the id/label
maps), and output `String`s (markdown, accessible names, metadata values).
This satisfies the acceptance criterion by construction, verified here by
direct code review as the task instructions explicitly allow ("harder to
test directly").

## Risks / follow-ups for the next task

- **Full W3C accname-1.2 algorithm** (`aria-labelledby`, visibility
  exclusion, presentational-role handling) is a real, disclosed gap - the
  highest-value follow-up if a later task's automation/locator work
  (M3-T02) needs accessible-name-based element resolution to match what a
  real browser's accessibility tree would compute.
- **No reference/WPT-style semantic-extraction/markdown-generation
  conformance corpus exists** - unlike tree construction (html5lib-tests)
  or selectors (WPT's own selectors suite), there is no widely-adopted
  standard corpus for "accessible name + markdown readability" to vendor
  against; a dedicated task should still define and build a larger
  hand-authored regression corpus as this feature area matures, mirroring
  the `tests/wpt/` pattern used elsewhere in this repository for the parts
  of the stack that do have a standard corpus.
- **`tabindex`-only custom-widget interactivity** and **`form="other-id"`
  cross-tree control association** are both real, bounded gaps named above
  - low-risk, well-isolated follow-ups if a later task's automation surface
  needs either.
- **No true pagination/cursor-based continuation for markdown generation**
  past a truncation point - a caller needing the remainder of a very large
  document today has no API to request "the next chunk" from this crate; a
  scoped-subtree extraction entry point (`generate_markdown_from(document,
  root: NodeHandle, ...)`) would be a natural, small follow-up.
- **This crate's own `walk_document_order` duplicates the *shape* of
  `machina_selectors::query::walk_document_order`** (that function is
  `pub(crate)` to `machina-selectors`, not exported) - if a later task finds
  itself needing the same shared walk in a third crate, exporting it from
  `machina-selectors` (or extracting it to a tiny shared internal-only
  crate) would be a reasonable, low-risk consolidation; not done here to
  avoid modifying `crates/selectors` outside this task's read-only scope.
